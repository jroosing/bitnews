# internal/web

The browser UI: server-rendered HTML with htmx, Tailwind CSS and Alpine.js (CSP build), embedded in the binary. Decisions and trade-offs are in [ADR-0005](../../docs/adr/0005-web-ui-stack.md); the milestone design is in [docs/milestones/m6-ui.md](../../docs/milestones/m6-ui.md).

```
internal/web/
  web.go, pages.go, handlers_auth.go  New(Deps), routes, the Page table, login/logout/setup
  middleware.go, errors.go            CSP + headers, auth failures as pages, safeNext
  assets.go, render.go, head.go       asset hashing + /static/, renderComponent, View, head asset URLs
  hx.go, comp_icon.go                 Hx (typed htmx attributes), Icon component
  icons_gen.go                        generated by scripts/gen-icons.sh (Heroicons): IconName constants
  layout.templ, comp_*.templ          layouts, head, nav, shared components (templ, ADR-0011)
  page_*.templ                        one file per page and its fragments
  *_templ.go                          GENERATED by `make generate`, committed
  src/app.css                         Tailwind source: tokens (@theme), components (@layer)
  assets/static/                      app.css (GENERATED, committed), js/, vendor/, fonts/, VENDOR.md
```

## Rebuilding the CSS

`assets/static/app.css` is generated and committed, so `go build` and CI need no Tailwind step. After changing a `.templ` file, `src/app.css` or `assets/static/js/*.js` (Tailwind scans them for class names), run:

```
make css          # one-off, minified
make css-watch    # while designing
make css-check    # fails if the committed file is stale (not run in CI)
```

The standalone CLI (no node) is downloaded and SHA-256-verified into `bin/tools/` by `scripts/get-tailwind.sh` on first use. Class names must appear as complete strings in a `.templ`, JS or Go file: `"bg-" + colour` is never generated. Component classes (`btn-primary`, `badge-ready`, ...) are plain CSS in `src/app.css` and are always present.

Design tokens are CSS variables in the three `TOKENS` blocks of `src/app.css` (light, dark by media query, dark by `data-theme`). Change the accent there, in one place. `TestTokensMeetContrastAA` parses these blocks and fails if a text pair drops below 4.5:1 or a non-text pair below 3:1.

## Views (templ)

The HTML is written as [templ](https://templ.guide) components (ADR-0011): `.templ` files in this package, compiled to committed `*_templ.go` files. After changing one run `make generate` (`make generate-check` fails when a generated file is stale; it is part of `make check`, not of CI). The generator is pinned as a `tool` in `go.mod`, so `go tool templ ...` needs no install. Run `make css` as well when you add classes.

- Pass the typed page or view structs; no `map[string]any`. Components with more than about three parameters take a props struct (`ButtonProps`, `FieldProps`, ...); enum-like values are named string types with constants (`BadgeState`, `AlertVariant`, `ButtonVariant`, `IconName`).
- htmx wiring: static attributes are written inline; dynamic ones go through `Hx{...}.MustAttrs()` (`hx.go`), which only expresses the attributes in the struct, requires relative URLs and ID-shaped `Vals`. An invalid `Hx` panics with an `hxError`, which `renderComponent` turns into a 500.
- Links: `href={ templ.URL(x) }`, never `templ.SafeURL` (it skips the check that neutralises `javascript:`).
- templ drops the whitespace between tags written on separate lines; write `{ " text" }` where a visible space is needed. A `@Component(...)` call must be on its own line, and a text line that starts with `if`, `for` or `switch` must be wrapped in `{ "..." }`.

## CSP rules for views

The CSP forbids inline script, inline style and eval. Tests render every page and fail on any of these, so do not use them:

- no `<script>` without `src`, no `<style>`, no `style="..."` attribute;
- no `on*` attributes and no `hx-on*` (put behaviour in `js/app.js`);
- no `javascript:` URLs; URL attributes take relative paths only;
- progress is a `<progress>` element (never an inline width);
- Alpine: use the CSP build's supported expressions, and reference components registered with `Alpine.data` in `js/app.js`. Never put data (names, IDs) into an Alpine expression: write it into a `data-*` attribute and read it in a method.

Every dynamic value is escaped by templ. Download names are hostile input. `hx-vals` and similar attributes are built only from server-validated IDs through `Hx.Vals`, never from names.

The document head links assets by their hashed URLs (`headAssets` in `head.go`, resolved once at startup). Icons are `@Icon(IconQueue, "size-5")`.

## Add a page

1. Create `page_<name>.templ` with a component that wraps its content in `@AppLayout(v, subtitle, actions)` (both slots may be `nil`; the layout supplies the `<h1>` from the page title), then run `make generate`.
2. Add a `Page{Path, Component, Title, NavLabel, NavIcon, Data}` to `builtinPages()` in `pages.go` (or call `s.addPage(...)` from your own `routes_<name>.go`, invoked from `registerRoutes`). A page with a `NavLabel` appears in the sidebar; without one it is hidden. `Data` returns what `Component` receives as its second argument.
3. Page routes already sit behind `UIAuth` and CSRF; an unauthenticated browser is redirected to `/login?next=...`.
4. `make css`, then check the page in the style guide's light, dark and 390 px views.

## Add a fragment or action route (htmx)

Register it in `registerRoutes` (or your `routes_<name>.go`) with `s.handleAuthed("POST /queue/{id}/pause", handler)`. In the handler:

- Services come from `Deps` (add fields to `Deps` as pages need them; `New` only requires the auth services and Settings).
- Render a fragment with `s.renderComponent(w, r, status, QueueRow(row))`, where `QueueRow` is a templ component. Fragments are swapped in by htmx.
- Redirect with `s.redirect(w, r, "/path")` (HX-Redirect for htmx, 303 otherwise).
- Show a toast by setting `HX-Trigger: {"toast":{"level":"success","message":"Saved"}}`. Levels: success, info, warn, danger.
- A form must also work without JavaScript: give the `<form>` a real `method` and `action`, and add `hx-post` for the enhanced path.
- `s.renderError` answers with an error page, or a toast for htmx. Errors from the auth middleware are converted automatically.
- Destructive buttons: put `hx-confirm="..."` on the element (optionally `data-confirm-tone="danger"` and `data-confirm-label="Remove"`); `app.js` shows the styled dialog instead of `window.confirm`.

## Add a component

Components are templ functions in `comp_*.templ`. Containers that wrap arbitrary content take `{ children... }` (`Card`, `Modal`, `TableShell`). Add the component to `page_styleguide.templ` (every state), and add its classes to `src/app.css` under `@layer components` when it needs more than utilities.

Naming: templ components are CamelCase (`EmptyState`, `Card`); CSS component classes are lower-case with hyphens (`btn-primary`, `badge-ready`); Alpine components are camelCase (`confirmDialog`).

Components: `button`, `field` (text/password), `select_field`, `checkbox_field`, `switch_field`, `badge`, `card_start/end`, `empty_state`, `alert`, `auth_banner`, `table_start/end`, `modal_start/end`, `confirm_dialog`, `toast_region`, `progress`, `pagination`, `copy_button`, `csrf_field`, `settings_layout_start/end`, `settings_form_start/end` (see [Settings sections](#settings-sections)).

## Live updates (`/ui/events`)

Every app page opens one SSE connection (`hx-ext="sse" sse-connect` on `<body>`; the queue page adds `?rows=1`). The server renders HTML, not JSON, and sends named events that the `#live-sink` element swaps out of band: `status` (the top bar's `#status-down`, `#status-up`, `#status-queue`; keep those IDs), `live` (the changing cells of queue rows: `dl-<id>-status|progress|speed|eta`) and `removed`. `refresh` and `resync` make `#queue-lists` refetch `/queue/fragment`, and `js/queue.js` refetches whenever the stream (re)opens, because events are not replayed. Bus events are only noted on arrival and rendered once per tick (1 s), so a Download is updated at most once a second per connection. The stream drops a client that does not read within the write timeout and ends on shutdown.

Queue actions are `POST /queue/{id}/pause|resume|priority|move|category|remove` and `POST /queues/{usenet|torrent}/pause|resume|speed`. They answer htmx with the updated row or the whole lists, and errors with a toast (`HX-Trigger`) and a `queue-refresh`. A limit set on the queue page is temporary (lost on restart, and replaced when the speed settings change); the saved limits are on Settings, Speed & queue. Ready torrents that keep seeding are on the History page, not in the queue.

## Static files

`/static/<name>` is served from memory by exact lookup. The head links `js/app.js` through `headAssets`, which holds `/static/js/app.<hash8>.js` served `immutable`; the plain name revalidates. CSS `url()` references are rewritten to hashed names at startup. Vendored files and their integrity are listed in `assets/static/VENDOR.md` (`scripts/vendor-web.sh`).

## Settings sections

Settings is one area with a section per page: `/settings` redirects to the first section, and each section lives at `/settings/<slug>`. The shell is in `settings.go`, the section list is a table there, and every section page is wrapped by the `settings_layout_start` / `settings_layout_end` components (section navigation: a scrollable pill bar below 768 px, a sticky sidebar from there up).

### Registry

`settingsSections()` returns the `SettingsSection` entries: `Slug`, `Title`, `Icon`, `Description`, `Order` (navigation order; the lowest is where `/settings` leads), `Component` (required), and optionally `Data` and `Routes`. There is no placeholder page: a section exists once it has a component. Currently, in navigation order: `paths`, `servers`, `speed`, `postprocessing`, `torrent` and `security`.

To add a section (for example Speed & queue):

1. Create `page_settings_speed.templ`: `@AppLayout(v, subtitle, nil)` around `@SettingsLayout(p.Nav)`, with the cards inside. The section's own data is `p.Data`.
2. Add a registry entry and set `Component: SettingsSpeedPage`, `Data: settingsSpeedData` (func `(s *Server, r *http.Request) (any, error)`) and `Routes: (*Server).registerSpeedRoutes`.
3. In `settings_speed.go` write the data func and `registerSpeedRoutes` (`s.handleAuthed("POST /settings/speed", ...)`). Prefix package-level names with the section so files do not collide.
4. `make css`, then check the page in light, dark and at 390 px.

### Paths & Categories

Saving the folders checks their shape only, through `core.Paths.Problems` (absolute, clean, no `..`, the incomplete and complete folders of both protocols not nested), and shows each problem next to the folder at fault (422, nothing saved). It never looks at the disk: no exists, writable or same-filesystem check, no warning for a folder that is missing, and nothing is created on save (bitnews creates missing folders when the first download needs them, see ADR-0006 and M7-01). A category's folder override gets the same shape check (`pathShapeError`). The page hint tells the user to keep the complete folders and the media library on one filesystem, because Sonarr and Radarr make the hardlinks, not bitnews. Changed by M7-01; earlier versions of this page probed the folders (`pathChecker`) and warned about different filesystems.

### The settings form pattern

A card with one `<form>` per group of settings, so every card saves on its own:

```
@SettingsForm(SettingsFormProps{ID: "speed", Action: "/settings/speed", Title: "Speed limits", Subtitle: "...", Error: v.Error, Saved: v.Saved, Dirty: v.Dirty, Label: "Save limits"}) {
  ...the Field / SelectField / SwitchField components, <fieldset><legend> for groups...
}
```

- The card is `#<ID>-card`; the form posts with `hx-post` and the response **replaces the whole card** (`hx-swap="outerHTML"`), so errors, warnings and the clean state all come from the server. Render it from a component (`SpeedLimitsCard(view)`) and answer with `s.renderComponent(w, r, status, SpeedLimitsCard(view))`.
- Read the current Settings, replace only your part and call `Settings.Update`: `next := s.Settings.Current(); next.Queues = ...; s.Settings.Update(ctx, next)`. Never build Settings from scratch, or Auth, Network and Seeding are lost.
- Validate per field before calling the service and answer `422` with the card (htmx swaps `422`); set `Error` on each `field` (it renders the message with `aria-describedby` and `aria-invalid`), keep what the user typed and set `Dirty` so Save stays enabled. A problem that belongs to no field goes into the form's `Error`. A service error: `settingsAppError(err)` gives the `*app.Error` with its message.
- On success send a toast with `settingsTrigger(w, "success", "Saved.", nil)` (use `"warn"` when you also show warnings) and re-render the card. Without htmx (plain POST) render the whole page with `s.renderSettingsPage(w, r, status, "speed", data)` and set `Saved`.
- Save is disabled until a field changes (Alpine `settingsForm`, in `js/settings.js`) and shows a spinner while the request runs (the form gets `htmx-request`). Unsaved changes show "Unsaved changes".
- Non-blocking remarks (for example a note about what a saved value means for running downloads) are an `alert alert-warn` block inside the card, computed on the server after the save.

### Speed & queue and Torrent network (`settings_cards.go`)

These two sections are made of several cards that each edit one slice of `core.Settings`. `settings_cards.go` holds the shared machinery: a `settingsCard` says how to turn the Settings into form values (`values`), how to parse and validate the form into a copy of the current Settings (`read`, one message per field name), optionally which saved values still wait for a restart (`restart`, compared with `Deps.Config.Started()`) and an extra view (`view`). `registerCards` adds the POST route; `cardPage` builds `.Page.Data` as a map keyed by card (`views := p.Data.(cardViews)`, then `SpeedQueueCard(viewOf[cardView](views, "queue"))`). The card templates read `.V` / `.E` (values and errors by field name), so a failed save shows exactly what was typed. Numbers are parsed by `wholeNumber` / `decimalNumber`, which accept plain ASCII digits only.

`Deps.Config` (`ConfigSource`) is optional: it gives the settings the daemon started with (for the "Saved, waiting for a restart" notes) and the live status of the Usenet and torrent network bindings (bound, unavailable and why, not bound). Speed limits, queue sizes, `min_free` and the Share Limit defaults apply at once (the daemon reacts to `core.SettingsChanged`); the torrent engine options, the network bindings and post-processing concurrency are read at start-up.

### Post-processing (`settings_postprocessing.go`)

One card on the card engine with two switches that edit `Settings.PostProcess`: `clean_names` (strip bot tags from an NZB's name when it is added) and `underscores_to_dots` (rename the result's top-level names after Unpack). A switch is a checkbox, so the form has no invalid state: an unticked box is simply absent and means off. The options apply to the next download, so the card has no restart note. Each switch is a `postprocessing_option` block in `settings_postprocessing.html`: the switch with its help, then when it runs, an example and a note.

### Rows, dialogs and probes

The Usenet servers section shows the other patterns: a table whose rows swap one at a time (`server_row`), an add/edit dialog whose form is loaded by htmx into one `<dialog>` (Alpine `serverDialog` opens it when the form arrives and closes it on the `dialog-close` event that a successful save sends in `HX-Trigger`), and inline results of a test request (`probe_result`). A successful save answers with `HX-Retarget` and `HX-Reswap` so the list is swapped while the dialog form is the default target for errors.

Write-only secrets: never put a secret into a `value` attribute; an empty password field means "keep the stored one".

### Tests

Handler tests live in `settings_test.go`, `settings_security_test.go`, `settings_paths_test.go`, `settings_categories_test.go` and `settings_servers_test.go`: `settingsSignedIn(t, opts...)` gives an env and a signed-in browser, `settingsPost` / `settingsDo` send htmx requests with the CSRF header, `withProber` replaces the connection prober. Add the new section's pages and fragments to `addSettingsResponses`, so the shared HTML invariant tests (no inline script or style, accessible names, unique ids) cover them.

## History, Download detail and the "New download" dialog

- `history.go`, `history_format.go`: `/history` filters (state, type, category) go in the query string; the form works without JavaScript and, with htmx, swaps `#history-results` out of the full page response (`hx-select`). The Download service lists oldest first with a forward cursor, so the page reads all Ready and Failed Downloads and sorts them newest first itself (by `ReadyAt`, else the last update); its cursor is `before=<unix nanoseconds>-<id>`.
- `detail.go`: `/downloads/{id}` (IDs are checked against the core.ID shape first), `/downloads/{id}/live` (the part htmx polls every 3 s; it carries the trigger only while the Download is not Ready or Failed), `POST /downloads/{id}/delete` (`delete_data=1` also deletes files) and `POST /downloads/{id}/share-limit` (torrents). Failure wording per `core.FailureReason` is in `history_format.go`; add a reason there when core gets one.
- Every fact of a Download that the queue rows, the live cells, the history and the detail page show (badge word, progress, rates, ETA, Post-processing stage, torrent peers, ratio and Share Limit, the cleaned failure detail) comes from its View (`Deps.View`, `internal/view`, ADR-0008); the UI only formats it (`badgeOf`, `progressPercent`, `formatETA`). The queue row and the detail page use the same words, the Phase's (`Unpacking`, never `Extracting`). `Deps.View` is required with `Deps.Downloads`; tests give it a fake `view.LiveSource` (`env.live`).
- `Deps.Detail` (the Usenet Article report, the runner's `FetchDetailOf`) is what the View does not give; it may be nil. A torrent's files come from the View, and its Share Limit is set through `DownloadService.SetShareLimit`.
- `add.go`, `layout.templ` (`AddDialog`, `AddForm`), `js/detail.js`: the global dialog loads its form from `GET /downloads/add` on the `add-open` window event (any element with `data-add-open` fires it) and posts multipart to `POST /downloads/add`. Refused adds answer with the status of the problem (400, 409, 413, 502, 503) and the form with its errors; `detail.js` lets htmx swap those. Success sets `HX-Trigger` with a toast, `download-added` and `queue-refresh`. `/downloads/add` is the only route with a body limit above 64 KiB (`uploadLimits` in `detail.go`).
- htmx is configured with `attributesToSettle` without `style`: htmx would otherwise copy `style` attributes between old and new elements with the same id, which is an inline style (blocked by the CSP) and wipes what Alpine's `x-show` set.
- `.table-responsive` forces `display: block` below 768 px (the Tailwind `table` utility on the same element would win otherwise).

## Settings: Security

`settings_security.go` (registry entry, page data, list parsing) and `settings_security_{access,password,keys,adapters}.go`, one file per card, all on `pages/settings_security.html`.

- **Sign-in and hosts** (`/settings/security/access`, `/hosts`): read `Settings.Current()`, replace only `Auth`, `Update`. Enabling disable-auth or LAN bypass needs an allowed host that includes the Host the browser used (else a field error, so the user cannot lock themselves out). Newly turning sign-in off, adding LAN networks, or trusting proxies while bypass is on answers `200` with a confirm card (`security_confirm`): the values come back as hidden fields plus `confirmed=1`, so confirming is a plain post and nothing is kept on the server. Cancel is `GET` of the card.
- **Password** (`/password`): `auth.SessionService.ChangePassword` checks the current password through the login limiter (429 + `Retry-After`), applies the length rules, rehashes with the current argon2 parameters and ends the user's other sessions (`SessionRepo.DeleteForUserExcept`). Not offered to bypass or disabled-auth principals.
- **API key** (`/app-key`, `settings_security_appkey.go`): one card for the one key of the app (ADR-0006). The key is plain text in the card (a `<code>` and the Copy button) and nowhere else in the HTML. The copy-ready Sonarr/Radarr values come from the request Host (host and port, rendered escaped, so a hostile `Host` header is inert), `sabnzbd` as the URL base and the fixed qBittorrent username `bitnews`. `POST /settings/security/app-key` is Rotate: without `confirmed=1` it answers with the confirm step (`security_confirm`, works without JavaScript) and changes nothing; with it, `auth.AppKeyService.Rotate` makes a new key that is valid at once on the API, SABnzbd and qBittorrent and ends the qBittorrent sessions. The key is never in a toast or the log. There are no key routes in the API.
